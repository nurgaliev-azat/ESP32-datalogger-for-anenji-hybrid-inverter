## Экономия GitHub и API
- Использовать GitHub connector для чтения и записи в доступном репозитории; не запускать внешние скрипты, когда хватает штатных операций.
- Перед изменениями получить дерево/список нужных путей и HEAD один раз; читать README, состояние и целевые исходники, не сканировать весь репозиторий повторно.
- Сгруппировать связанные изменения в один логический коммит или pull request, особенно при изменении нескольких файлов. Проверять SHA перед заменой файлов; избегать перезаписи параллельных изменений.
- Не делать пустых коммитов и не выполнять повторное чтение неизменённых файлов. Для нескольких независимых проверок допустим ограниченный параллелизм; записи в один путь — только последовательно.
- API: переиспользовать результаты уже полученных чтений, делать пагинацию только по необходимости; отслеживать rate limits, backoff и Retry-After для 429/5xx; ограничивать повторы, не повторять неидемпотентные POST без ключа идемпотентности или сверки результата.
- Минимизировать поля ответов, объём логов и размер отправляемого контекста; применять кэш с разумным TTL, если данные не секретные и согласованность допускает.
- Никогда не помещать токены, ключи API, персональные данные и конфигурацию продакшена в коммиты или логи. Использовать secrets/переменные окружения, минимальные permissions и отдельные лимиты расходов.
- Для платных ИИ API: применять квоты на пользователя/агента, max tokens, тайм-ауты, бюджетные предупреждения и отключение запросов при достижении лимита; админ-панель расходов — только администратору.
- Внешние API-запросы и реальный расход денег запускать лишь по необходимости; тестировать с mock/stub, когда можно.
